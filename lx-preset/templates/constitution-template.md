## Governance — жизненный цикл спецификаций

<!-- Правила, которые в Leadaxe были неявными. Здесь кодифицированы явно. -->

- **Спецификация живёт вечно.** Один номер = одна папка; папки не удаляются даже при закрытии без кода.
- **Статус — во front-matter SPEC** (`Status:`), не в имени папки: `New → Open → Merged → Shipped → Complete`; особый терминал — `Closed-no-impl` (карточка закрыта без реализации, сохранена как референс).
- **Одна фича — один SPEC.** Дубликаты консолидируются (поле `Consolidates`).
- **Спецификация — слой документации.** Инвариант в SPEC ↔ guard-тест `test_specNNN_invM` (код-якорь + проверка); связь двунаправленная и поддерживается.
- **Анти-подкрутка (v4.4).** Падающий guard-тест чинится в коде; ослабление предиката/контракта — только явной правкой SPEC «Инварианты». Расхождение кода со спекой — баг в коде, не в спеке.
- **Constitution Check обязателен** в каждом PLAN до реализации.
- **Изменения фиксируются в release notes** и привязываются к версии; schema bump объявляется в SPEC.
- **Формат коммит-сообщений.** Conventional Commits (`type(scope): subject`); subject и body —
  на английском (технические идентификаторы и цитаты из SPEC — как есть); коммит, реализующий
  или правящий SPEC, несёт суффикс `SPEC-0NN` в subject
  (напр. `feat(infra): scoped no-Delete IAM user SPEC-022`). Merge-коммиты освобождены.
- **Ветки по умолчанию ребейзятся.** Feature-ветка обновляется `git rebase main` (линейная
  история поверх main), НЕ merge'ем main в ветку. Merge-коммит допустим при интеграции ветки
  в main. Push переписанной ветки — только `--force-with-lease`.
