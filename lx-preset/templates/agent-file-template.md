## Что читать первым
- **Constitution** — приоритеты, архитектурные инварианты, запреты, язык.
- **SPEC/PLAN/TASKS текущей задачи** — перед любой правкой кода.
- **docs/ARCHITECTURE.md** — слои, зоны ответственности, потоки данных.

## Scope агента (строгий контроль)
- Читать можно любые файлы. **Изменять — только покрытое SPEC/PLAN/TASKS** текущей задачи.
- Выход за рамки (другие файлы, новые файлы вне PLAN, смена архитектуры/public API,
  перемещение файлов) — **остановиться и спросить**, не делать по своей инициативе.

## Философия разработки
- **Код — обязательство, а не актив.** Лучший код — не написанный. Сначала спроси: можно ли решить удалением/упрощением?
- **Простота важнее абстракции.** Интерфейс — при ≥2 реализациях или нужде в моках. Обёртка без логики — шум.
- **Единственный источник правды.** Не дублируй данные и константы.
- **Обратная совместимость — функциональная, не API.** Сохраняй поведение, свободно меняй внутренние сигнатуры; ломающий вызывающий код — исправляй, а не оборачивай.
- **Удаление кода — тоже результат.**
- **Думай данными, а не кодом.** Правильная структура данных делает код очевидным.

## Git (ограничение)
- **Никаких git-действий без явного указания:** нет commit/push/pull, веток, rebase/merge, изменения истории, `.gitignore`, hooks.
- По умолчанию работа локальная, результат — предлагаемый дифф. Нужен git — остановись, объясни зачем, спроси.
- (В Spec Kit это обеспечивается тем, что расширение `git` НЕ установлено.)
- **Формат коммита (когда коммит явно разрешён):** Conventional Commits + ссылка на спеку в конце
  subject'а — `type(area): subject SPEC-NNN (Phase N)`. `area` = область кода (не номер спеки);
  `SPEC-NNN` — только для спековых коммитов, `(Phase N)` — когда есть фаза; инфраструктурные коммиты
  без ссылки. Грепается `git log --oneline | grep SPEC-NNN`.

## Контракт выхода (после реализации)
1. Краткий план изменений (1–3 пункта). 2. Список изменённых файлов (полные пути).
3. Ключевые фрагменты кода (с путями), не простыни. 4. Команды проверки (build/test/vet/линтер).
5. Риски и ограничения. 6. Assumptions, если ТЗ было неполным.

## Язык по ролям
- Проза (SPEC/PLAN/TASKS/REPORT), ответы в чате — **русский**.
- Код, UI, технические ошибки, имена, **комментарии в коде — английский** (длинные пояснения допустимы на русском).
