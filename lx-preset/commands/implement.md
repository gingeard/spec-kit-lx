## LX: правила реализации

Реализуя задачи из `tasks.md`, дополнительно к ядру выше соблюдай:

1. **Минимальный дифф.** Меняй только то, что покрыто SPEC/PLAN/TASKS. Никаких самовольных
   рефакторингов, переименований, новых файлов/зависимостей вне PLAN — иначе остановись и спроси.
2. **Философия:** простота важнее абстракции; единственный источник правды; удаление кода — результат;
   не оборачивай без логики; думай данными, а не кодом. Идиоматичный стиль языка проекта.
3. **Проверь существующие утилиты** перед написанием новой функции (логирование, константы,
   контекст/таймауты, платформа, доменные хелперы).
4. **Логирование** в ключевых точках новых участков: start / success / error. Секреты/PII не логировать.
5. **Инварианты.** Не нарушай архитектурные инварианты Constitution и инварианты SPEC. Подтверди их
   guard-тестами `test_specNNN_invM_*` (source-scan/поведение) — прозу-маркеры `// SPEC …` в код НЕ пиши (D14).
6. **Git — только по явному указанию.** По умолчанию результат — предлагаемый дифф, без commit/branch/push.
7. **После реализации выдай контракт выхода:** план изменений, изменённые файлы (полные пути),
   ключевые фрагменты, команды проверки (build/test/vet), риски, Assumptions.
8. **Каждая фаза оставляет ветку зелёной.** Не переходи к следующей фазе с красными build/test/vet.
9. Когда все задачи выполнены — не забудь **фазу «Закрытие»** из tasks.md (отчёт, release notes,
   статус, трассировка). Её автоматизирует `/speckit.lx.close`.
