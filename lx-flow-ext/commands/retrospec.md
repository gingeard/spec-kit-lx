# /speckit.lx.retrospec — обратная спека по существующему коду

Реверс-инженерь **одну** описательную спецификацию для уже написанного кода.
Это НЕ forward-цикл (spec→plan→tasks→implement): код уже есть, ты документируешь
«что есть и почему». Ничего не коммить в git; кода НЕ меняй (кроме предложенных
маркеров — их только предлагай, не проставляй без подтверждения).

## Аргумент
Слот из инвентаря (см. `spec-inventory.sh`) в свободной форме, например:
`012 F core/config/subscription — парсер подписок, git a1b2c..e3f4d` — или просто
область кода + краткое имя, если инвентаря нет.
Опции набора артефактов: `--full` (spec+plan+tasks+report) · `--artifacts spec,plan,report`
(по умолчанию — только spec + предложенные маркеры).

## Прочитай (контекст)
1. `SPECS`/`specs/` — соседние спеки (формат, номера, чтобы не пересечься и корректно проставить `Depends on`).
2. Constitution — словарь инвариантов и запретов (на них ссылаться, не выдумывать новые).
3. Код области слота: публичные типы/функции, границы, поведение.
4. Git по этой области: `git log --oneline -- <path>` и, если задан диапазон, сообщения коммитов/PR — источник «почему».
5. release notes / теги — в какой версии это вышло.

## Кислотный тест (обязателен) — иначе не пиши спеку
Спека имеет право на существование, только если несёт то, чего **в коде нет**:
намерение, отвергнутые альтернативы, инвариант, ограничение. Если получается лишь
пересказ кода — **не создавай спеку**, доложи «слот не несёт знания сверх кода —
пропустить/консолидировать» и остановись.

## Собери descriptive-SPEC
Скаффолд можно взять `/speckit.specify`, затем перезаполнить как ОПИСАТЕЛЬНУЮ (не план):

- **Front-matter:** `Status: Complete (C)` или `Shipped (S)`; `Type` (F/B/R/Q — по характеру, из commit-префикса, если есть); `Depends on:` — из реального графа импортов области; `Release:` — версия/тег, где вышло; `Bump:` — если вводило/менял схему.
- **Проблема / Контекст:** зачем это существует. Тяни из сообщений коммитов, PR, release notes. Чего не найдено — реконструируй из кода и **явно помечай `[реконструкция]`**, не выдавай догадку за факт.
- **Инварианты (что НЕ меняется):** какие несущие свойства область удерживает; ссылайся на Constitution и соседние SPEC.
- **Вне scope:** что сознательно НЕ входит в эту способность.
- **Критерии (поведение-как-есть):** текущее наблюдаемое поведение как контракт (то, что нельзя сломать), а не будущая цель.
- **Связи:** Зависит от / Референс + список файлов области.

## Комплементарные артефакты (as-built, опционально)

По умолчанию — только `spec.md`. Для крупного слота или полного канона Leadaxe собери ретро-версии
остальных: флаг `--full` (spec+plan+tasks+report), либо перечисли `--artifacts spec,plan,report`.
Все — в жанре **AS-BUILT** (что есть), а не forward (что построить). Кислотный тест применяется к
КАЖДОМУ: не плоди артефакт, лишь пересказывающий spec/код.

- **invariants.md** — если инвариантов ≥3, вынеси их в матрицу (`утверждение·код·тест·провенанс·маркер`),
  а в spec оставь терсный ИНДЕКС + ссылку. `тест: —` → дыра покрытия (кандидат в тест-заглушку). При <3 — инлайн в spec.
- **plan.md (as-built)** — «как построено»: таблица `файл · символ · роль` (развёрнутая «Где живёт»),
  ключевые решения (почему так — реконструированные из кода/коммитов), Constitution Check
  (какие инварианты соблюдены), порядок фаз из git-истории (если полезно).
  → Ценно для сложной подсистемы; для мелкого слота избыточно (хватает «Где живёт» в spec).
- **tasks.md (as-built)** — чеклист того, что БЫЛО сделано (всё `[x]`), по подсистемам, + фаза
  `## Закрытие` (done). ⚠️ Для ретро **низкая ценность** — done-чеклист повторяет критерии spec;
  генерируй только если нужен полный канон или карта покрытия тестами.
- **implementation_report.md (as-built)** — `## Итог · ## Изменения (файлы/функции) · ## Решения ·
  ## Проверки (какие тесты покрывают) · ## Безопасность · Дата/версия`. Это `/speckit.lx.report`
  в as-built-режиме — можешь просто вызвать его после spec.
- **design** — НЕ генерируется отдельным файлом. Есть forward design-доки (`docs/…/*-design.md`) —
  сошлись на них в spec «Связи · Референс». Нет — дизайн-рациональ живёт в самом spec
  (`Проблема` + `Отклонённые альтернативы`), а не в `design.md` (иначе дубль).

Порядок: `spec.md` первичен, остальные — производные от него и кода, не дублируют. Каждый несёт
ту же мета-шапку (`Status`/`Type`/`Release`) и статус AS-BUILT.

## Маркеры трассировки
Предложи (не проставляй сам) точки в коде для `// SPEC NNN invariant: …` — там, где живёт
инвариант области. Выведи список `файл:строка → предлагаемый маркер` для подтверждения.

## Выход
1. Пути созданных артефактов (spec + запрошенные plan/tasks/report). 2. Заполненный front-matter.
3. Что взято из git/notes vs `[реконструкция]`. 4. Список предложенных маркеров.
5. Флаг, если слот стоит консолидировать с существующей спекой.
6. Для каждого доп. артефакта — прошёл ли он кислотный тест (или пропущен как дубль).
После пачки слотов — прогони `/speckit.lx.trace` и `/speckit.analyze`.
