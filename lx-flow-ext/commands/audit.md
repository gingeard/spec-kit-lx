# /speckit.lx.audit — аудит кодовой базы по срезу

Проведи adversarial-аудит **существующего кода** в заданной зоне и оформи результат
как AUDIT-SPEC (жанр Q/аудит). Аудит читает КОД на дефекты и дрейф инвариантов —
не артефакты (это `analyze`) и не целостность связей (это `trace`). Ничего в git не
коммить; код НЕ меняй — только findings + предлагаемые фиксы/маркеры.

## Аргумент
Зона аудита в свободной форме: `core/config`, `protocol/wireguard + transport/*`,
«дельта форка vs upstream», диапазон файлов. Если не задан — уточни у пользователя scope.

## Прочитай (контекст)
1. Жанр-шаблон: `.specify/presets/lx/templates/audit-spec-template.md`
   (или `specify preset resolve audit-spec-template`) — это ФОРМА результата.
2. Constitution — инварианты и запреты (по ним судишь корректность).
3. SPEC'и, владеющие зоной (`specs/`/`SPECS/`): их разделы «Инварианты» — что обязано держаться.
4. Сам код зоны + тесты + git-blame ключевых мест (когда/почему появилось).

## Замести код (что искать)
Проходи по осям, не по одной: **логика · гонки/безопасность состояния · безопасность ·
производительность · наблюдаемость · документация · мёртвый код / недостающие маркеры**.
Каждый дефект — это конкретный сценарий отказа, а не «мне не нравится».

## Ранжируй и привязывай
Каждую находку оформи заголовком `#N · SEVERITY · класс · `file:line` · SPEC NNN`
(SPEC-владелец зоны, куда уйдёт фикс) и телом «Что / Почему дефект (сценарий) / Действие».
Уровни: **P0** (ломает прод) · **P1** (корректность/состояние) · **P2** (узкое/наблюдаемость/доки) · **P3** (nit).

## ОБЯЗАТЕЛЬНО: опровергни сам себя
Раздел **«Опровергнуто верификацией»** — не опционален. Каждое подозрение, которое НЕ
подтвердилось, вынеси с ДОКАЗАТЕЛЬСТВОМ, почему это не баг (чтение кода `file:line` /
тест `name` / замер / `[git]`). Аудит без этого раздела = непроверенные догадки
(«правдоподобный мусор»). Не выдавай гипотезу за дефект: если не смог подтвердить сценарий
отказа — это подозрение в «Опровергнуто», а не находка.

## Оформи AUDIT-SPEC
Создай `specs/NNN-<AUDIT_NAME>/SPEC.md` (номер — следующий; каркас можно от `/speckit.specify`,
затем перезаполни по `audit-spec-template`): Сводка по severity → findings P0–P3 →
Опровергнуто верификацией → Что здорово (baseline) → Рекомендация по приоритизации →
Связи (SPEC-владельцы, `[[память]]`, маркеры при фиксе).

## Выход
1. Путь аудит-спеки. 2. Сводка severity (счёт P0–P3 + опровергнуто). 3. Топ P0/P1 списком.
4. Что предлагается делать первым (блокеры релиза). Фиксы/маркеры — предложить, не применять.
Крупные фиксы P0/P1 → отдельные forward-SPEC'и (перечисли предложенные номера).
