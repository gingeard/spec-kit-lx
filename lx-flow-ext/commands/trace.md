# /speckit.lx.trace — проверка трассируемости

Проверь, что связи между спецификациями и кодом целостны. Только чтение и отчёт — ничего не меняй без подтверждения.

## Код → SPEC (машинная проверка каждого инварианта)
1. Возьми список изменённых/ключевых файлов текущей задачи (из plan.md / диффа / раздела «Где живёт»).
2. Разбери инварианты из секции «Инварианты» `spec.md` — блоки `**INVn — имя.**` + EARS-контракт
   (`WHEN/IF/WHILE/WHERE … SHALL …, NEVER …`) + `↳ **тип (ссылка).** почему`. Enforcement (код·тест·маркер)
   — из блоков `PLAN` «Инвариант-контроль». Сверь, что имена INVn в `spec.md` совпадают с блоками
   `plan.md` (рассинхрон spec↔plan → WARN).
3. **Маркеры / enforcement:** для каждого INV в `PLAN` «Инвариант-контроль» бери поля `Тест:` и `Маркер:`.
   Основная защита — guard-тест `test_specNNN_invM_*` (маркеры-комментарии в коде не обязательны, D14).
   Статус `☐ planned` (не `☑/✓ placed`) на Shipped/Complete-спеке → **FAIL** (защита декларирована, кода/теста нет).
   **Тип enforcement (v4.4, лестница):** скобка у теста — `(скан|символ|поведение|property|stateful|процедура)`.
   Учитывай тип в отчёте: `скан` на инварианте, двигающем деньги/состояние, → **WARN «слабый ярус —
   кандидат на апгрейд»**; `процедура` — осознанный потолок (не WARN, если помечен явно).
   Записи БЕЗ типа — легальны (спеки до v4.4): трактуй как раньше, тип в отчёте `—`, не FAIL/WARN.
4. **Код резолвится:** для каждого `Код: <file:symbol>` проверь, что `file` существует и `symbol`
   реально определён в нём — `grep -nE "def <symbol>\b|class <symbol>\b" <file>`. Не резолвится
   (файл/символ не найден) → **FAIL** (запись PLAN протухла: символ переименован/удалён/перемещён
   после того, как писался PLAN, — ссылка врёт молча, диф её не подсвечивает). `Код: —` при
   `☐ planned` — пропусти, это не дыра резолва, а ещё не реализовано.
5. **Тест резолвится и бьёт по символу:** для каждого `Тест: <name>` проверь `grep -rn "def <name>"
   tests/` — существует? Названный, но отсутствующий тест → **FAIL** (защита декларирована, но её
   нет). Затем внутри найденного теста проверь, что символ из `Код:` встречается в теле теста
   (`grep -A30 "def <name>" <test_file> | grep -n "<symbol>"`) — если нет, тест существует, но
   непонятно, что он на самом деле проверяет относительно заявленного `Код:` → **WARN**
   («тест не привязан к заявленному коду»), не FAIL (может проверять поведение через более
   высокоуровневую точку входа — это допустимо, но стоит явно пометить). `Тест: —` →
   **дыра покрытия** (WARN, не FAIL) — кандидат в тест-заглушку `test_<inv>` (red-phase);
   совпадает со списком в секции «Дыры покрытия» `spec.md`. Собери такие отдельным списком.
   **Словарь дыр (v4.4):** в «Дырах покрытия» spec.md различай `тест planned` (WARN — появится) ·
   `процедура` (не WARN — осознанный потолок, если указано «чем закрыто») · `косвенный guard`
   (INFO — защищено побочно). Дыра без типа — старый формат, трактуй как `тест planned`.
6. **Provenance (не FAIL):** тип в блоке `↳` — `требование (Rn)` / `принцип (§Const)` / `баг-инцидент (дата)`
   / `замер`, НЕ git-хеш (точный коммит даёт `git blame`). Если указан `Rn` / `SPEC NNN` — проверь, что
   такое требование/спека существует (висячая ссылка → WARN, не FAIL).
7. Сообщи об инвариантах без `placed`-маркера/теста, о нерезолвящихся `Код:`-ссылках и о файлах
   из «Где живёт», не покрытых guard-тестом.

## SPEC → SPEC
4. Разбери front-matter `Depends on` / раздел «Связи» текущего spec.md.
5. Убедись, что каждый упомянутый `SPEC NNN` существует (каталог `specs/NNN-…`), и что обратная
   ссылка уместна (напр. у задачи-источника есть «Порождает»).
6. Отметь висячие ссылки (на несуществующие/консолидированные номера) и предложи заменить на актуальные.

## SPEC → docs / release
7. Проверь, что заявленный `Schema bump` отражён (например, версия схемы в коде) и что для
   Shipped/Complete-статуса есть строка в `docs/release_notes/`.

## Дыры покрытия → заглушки (опционально, `--stubs`)

По умолчанию trace **только сообщает** дыры покрытия (read-only). С флагом `--stubs` — сгенерируй
**red-phase заглушки** для инвариантов с `Тест: —` (из секции «Дыры покрытия» `spec.md` —
там уже предложены имена `test_<inv>`):

- Для каждой дыры создай функцию в подходящем `tests/test_<module>.py` (по `Код: file:symbol`):
  ```python
  import pytest

  @pytest.mark.xfail(reason="INVn not yet covered — see SPEC NNN «Инварианты»", strict=False)
  def test_<inv_name>():
      # ARRANGE/ACT: <как воспроизвести условие инварианта из его записи>
      # ASSERT: <что должно держаться> — сейчас падает (red-phase), снять xfail при реализации теста
      raise AssertionError("stub: реализуй проверку INVn")
  ```
- Имя бери из «Дыры покрытия» (`test_reconciliation_on_only_for_live` и т.п.), иначе синтезируй из утверждения.
- НЕ трогай продовый код; только новые `tests/`. После — обнови `Тест:` в блоке PLAN «Инвариант-контроль» (`— → test_…`, статус ☐ planned остаётся до зелёного).
- Выведи список созданных заглушек; напомни, что `xfail`/`raise` держат их видимыми в CI, но не красят сборку.

## Выход
Таблица: `INV/связь | маркер | тип enforcement | код (резолвится?) | тест (резолвится? бьёт по символу?) |
провенанс (R/§/инцидент) | статус (OK/FAIL) | где исправить`.
Итог: `PASS` если у каждого инварианта есть placed-маркер, `Код:` резолвится в реальный символ,
реальный тест существует, и нет висячих SPEC/R-ссылок.
Провенанс без хеша — норма (не FAIL); `тест: —` — WARN (дыра покрытия); тест не бьёт по заявленному
символу — WARN. Нерезолвящийся `Код:` (символ переименован/удалён) — FAIL. Иначе `FAIL` со списком.
Отдельно — список «Дыры покрытия» (+ созданные заглушки, если `--stubs`). Без `--stubs` — только предложения.
