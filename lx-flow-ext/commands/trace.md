# /speckit.lx.trace — проверка трассируемости

Проверь, что связи между спецификациями и кодом целостны. Только чтение и отчёт — ничего не меняй без подтверждения.

## Код → SPEC (машинная проверка каждого инварианта)
1. Возьми список изменённых/ключевых файлов текущей задачи (из plan.md / диффа / раздела «Где живёт»).
2. Разбери записи инвариантов: если есть `invariants.md` — читай трёхстрочные записи
   (имя → EARS-контракт → привязки `код · тест · провенанс · §`); допустима и legacy-матрица
   (столбцы `Код · Тест · Провенанс · Маркер`). Иначе — инлайн-инварианты `spec.md`. Сверь, что
   ИНДЕКС в `spec.md` (имена INVn) совпадает с записями (рассинхрон → WARN).
3. **Маркеры:** `grep -rn "SPEC NNN" <исходники>`; сверь с секцией «Трассировка: маркеры».
   Любой пункт со статусом `planned` (не `placed`) или отсутствующий в коде → **FAIL** (связь односторонняя).
4. **Тесты / покрытие:** для каждого `тест: <name>` проверь `grep -rn "def <name>" tests/` — существует?
   Названный, но отсутствующий тест → **FAIL** (защита декларирована, но её нет).
   `тест: —` (host-only / нет) → **дыра покрытия** (WARN, не FAIL) — кандидат в тест-заглушку `test_<inv>`
   (red-phase). Собери такие в отчёте отдельным списком «Дыры покрытия».
5. **Provenance (не FAIL):** «почему» — это `R<n>` / `§<Const>` / `инцидент: …`, НЕ git-хеш (хеши
   намеренно убраны; точный коммит даёт `git blame`). Если `R<n>`/`SPEC NNN·R<m>` указаны — проверь,
   что такое требование существует (висячая ссылка → WARN, не FAIL). `[git <hash>]` опционален;
   если встретился — можешь проверить `git cat-file -e <hash>` (WARN при битом), но его отсутствие — норма.
6. Сообщи об инвариантах без маркера/теста и о файлах из «Где живёт», не несущих `// SPEC NNN`.

## SPEC → SPEC
4. Разбери front-matter `Depends on` / раздел «Связи» текущего spec.md.
5. Убедись, что каждый упомянутый `SPEC NNN` существует (каталог `specs/NNN-…`), и что обратная
   ссылка уместна (напр. у задачи-источника есть «Порождает»).
6. Отметь висячие ссылки (на несуществующие/консолидированные номера) и предложи заменить на актуальные.

## SPEC → docs / release
7. Проверь, что заявленный `Schema bump` отражён (например, версия схемы в коде) и что для
   Shipped/Complete-статуса есть строка в `docs/release_notes/`.

## Дыры покрытия → заглушки (опционально, `--stubs`)

По умолчанию trace **только сообщает** дыры покрытия (read-only). С флагом `--stubs` — сгенерируй
**red-phase заглушки** для инвариантов с `тест: —` (из секции «Дыры покрытия» `invariants.md`, если
она есть, — там уже предложены имена `test_<inv>`):

- Для каждой дыры создай функцию в подходящем `tests/test_<module>.py` (по `Код: file:symbol`):
  ```python
  import pytest

  @pytest.mark.xfail(reason="INVn not yet covered — see SPEC NNN invariants.md", strict=False)
  def test_<inv_name>():
      # ARRANGE/ACT: <как воспроизвести условие инварианта из его записи>
      # ASSERT: <что должно держаться> — сейчас падает (red-phase), снять xfail при реализации теста
      raise AssertionError("stub: реализуй проверку INVn")
  ```
- Имя бери из «Дыры покрытия» (`test_reconciliation_on_only_for_live` и т.п.), иначе синтезируй из утверждения.
- НЕ трогай продовый код; только новые `tests/`. После — обнови `Тест:` в `invariants.md` (`— → test_…`, статус остаётся до зелёного).
- Выведи список созданных заглушек; напомни, что `xfail`/`raise` держат их видимыми в CI, но не красят сборку.

## Выход
Таблица: `INV/связь | маркер | тест | провенанс (R/§/инцидент) | статус (OK/FAIL) | где исправить`.
Итог: `PASS` если у каждого инварианта есть placed-маркер и реальный тест, и нет висячих SPEC/R-ссылок.
Провенанс без хеша — норма (не FAIL); `тест: —` — WARN (дыра покрытия). Иначе `FAIL` со списком.
Отдельно — список «Дыры покрытия» (+ созданные заглушки, если `--stubs`). Без `--stubs` — только предложения.
