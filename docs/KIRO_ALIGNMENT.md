# Выравнивание шаблонов LX по Kiro: SPEC / PLAN / invariants

Ресёрч-документ: как перестроить шаблоны LX (`spec` / `plan` / `invariants`),
максимально сблизив их с трёхфазной моделью Kiro (`requirements` → `design` → `tasks`),
**сохранив** то, что есть в LX, и **добавив** то, что есть в Kiro, но отсутствует в LX.

Принцип переноса: `requirements ↔ spec`, `design ↔ plan`, `tasks ↔ tasks` — слоты уже
совпадают 1:1, поэтому это не перестройка конвейера, а **переименование секций +
перебалансировка содержимого** внутри уже существующих артефактов.

Легенда атрибутов: **О** — обязательная секция · **о** — опциональная · **У** — условная
(обязательна при выполнении условия). `(—)` в колонке Kiro — секция LX-native, прямого
аналога у Kiro нет (в скобках — ближайший по смыслу слот).

---

## 1. Отправная точка: три корпуса

| Модель | Артефакты на фичу | Ось «ЧТО/ЗАЧЕМ ↔ КАК» |
|--------|-------------------|------------------------|
| GitHub Spec Kit | 1 × `spec.md` + `plan.md` + `tasks.md` | spec = ЧТО/ЗАЧЕМ, plan = КАК |
| Kiro | `requirements.md` + `design.md` + `tasks.md` | req = продукт/бизнес, design = инженерия |
| LX (текущий) | `SPEC.md` (+ `invariants.md`) + `PLAN.md` + `TASKS.md` | SPEC = ЧТО/ЗАЧЕМ, PLAN = КАК |
| Leadaxe (первоисточник) | `SPEC.md` (freeform) + опц. `PLAN`/`TASKS` | SPEC = живой документ, источник инвариантов |

**Ключевое наблюдение.** Конвейер Spec Kit `spec → plan → tasks → implement` почти
1:1 ложится на Kiro `requirements → design → tasks`. `plan` уже занимает слот `design` —
меняется только имя-акцент, не порядок фаз (порядок фаз в Spec Kit расширяется hooks,
но не переставляется — совпадает с Leadaxe).

---

## 2. Ключевые решения этого ресёрча

| # | Решение | Обоснование |
|---|---------|-------------|
| D1 | **Имя `plan.md` / `/speckit.plan` держим**, меняем только содержание → Kiro-`design` | Ядро Spec Kit владеет командой/артефактом; переименование форкает naming-конвенцию, хуки, `analyze`. Ре-скоуп даёт 95% выгоды за 5% цены. «PLAN по имени — DESIGN по сути». |
| D2 | **Дизайн-секции уходят из SPEC в PLAN**: `Где живёт`, `Схема данных` | Это as-built КАК (Components / Data Models / API у Kiro), не требования. SPEC очищается до чистого requirements-документа. |
| D3 | **Sequencing уходит из PLAN в TASKS**: `Изменяемые/Новые файлы`, `Фазы реализации` | Это планирование работ (Kiro `tasks.md › Implementation Plan`), дублировало `tasks.md`. |
| D4 | **Инварианты — целиком в `invariants.md`** (durable-технический дом); из SPEC уходят, остаётся строка-ссылка | Инвариант — по оси предметной области **техника** («как не сломать»), не бизнес → не в бизнес-SPEC. По оси долговечности — **durable** → не в эфемерном PLAN. `invariants.md` удовлетворяет **обе** оси. |
| D5 | **Порога для `invariants.md` нет** — дом инвариантов независимо от их числа | Прежний порог `≥3` существовал, чтобы не засорять SPEC. Раз инвариантов в SPEC больше нет — порог не нужен: есть хоть один инвариант, он живёт в `invariants.md`. |
| D6 | **Режим «оба жанра»**: маркер `Жанр: Продукт (P) \| Инженерный (E)` + жанро-нейтральные секции | LX/Leadaxe — преимущественно systems-жанр (там «требование» само по себе инженерное), но целимся и в продуктовые фичи. Маркер сообщает читателю/тулингу оптику; для E-спек SPEC честно допускаем тонким (центр тяжести — PLAN + `invariants.md`). |
| D7 | **Порядок секций — Kiro-канон** | Introduction: Feature Summary → Business Value → Scope. Design: Security → Error Handling, Deployment → Migration. LX-native секции без Kiro-дома тукаются в конец соответствующего блока. |
| D8 | **`checklist` ≠ `invariants`** — не заменять одно другим | Ортогональны: checklist — эфемерный DoD-**гейт** (generic, галочка, протыкается раз перед закрытием); invariants — durable **контракт** (уникальная структурная запись). Свернуть инвариант в галочку = выбросить утверждение/провенанс/привязку. Связь: инвариантную секцию checklist'а **порождать** из `invariants.md` (гейт из источника истины). |
| D9 | **Ближайший родственник инварианта в ядре Spec Kit — Constitution**; `invariants.md` закрывает реальную дыру | Прочёсывание spec-kit: точного аналога нет. По духу (durable/непреложное) ближе всех Constitution — но это **системная** половина (широкие принципы, без привязки `file:symbol`/тест/маркер). Локальной половины (точечный код+тест-привязанный контракт) в ядре нет — её и заполняет `invariants.md`. Совпадает с делением LX: системные инварианты → Constitution §2, локальные → `invariants.md`. |

### Разбор D4 подробнее: инвариант по двум осям

Инвариант — гибрид, и его надо резать не по одному, а по обоим измерениям одновременно:

| Часть инварианта | Ось: предметная область | Ось: долговечность | Дом |
|------------------|-------------------------|--------------------|-----|
| Утверждение («guard всегда в начале») + §Const + почему | техника | durable (переживает redesign) | `invariants.md` |
| Привязка (`file:symbol` · `test` · маркер · дыры) | техника/impl | ephemeral (умирает с реализацией) | `invariants.md` (запись) + PLAN §Инвариант-контроль (как ЭТОТ дизайн держит) |

Отвергнутые альтернативы:
- **Оставить утверждение в SPEC** («разрез по шву») — держалось на допущении «SPEC = инженерные requirements». В режиме «оба жанра» для продуктового SPEC техническому утверждению не место.
- **Утащить инвариант целиком в PLAN** — ломает долговечность: PLAN эфемерен, при supersede плана утверждение умрёт. Инвариант — самое долговечное знание проекта.

## 6. Карта переноса (что куда уезжает)

```text
SPEC (было)                    →  куда уходит
──────────────────────────────────────────────────
Где живёт (карта кода)         →  PLAN §4  Где живёт (Components)
Схема / контракт данных        →  PLAN §5/6  Модель данных / API
   › Migration / back-compat   →  PLAN §12  Миграция и совместимость
Инварианты (полное тело)       →  invariants.md (дом), строка-ссылка ← остаётся в SPEC

PLAN (было)                    →  куда уходит
──────────────────────────────────────────────────
Изменяемые файлы               →  tasks.md  (задачи по файлам)
Новые файлы                    →  tasks.md  (задачи по файлам)
Фазы реализации                →  tasks.md  Implementation Plan (Phase 1…N)
```

## 7. Что добавляется из Kiro (не было у LX)

- **SPEC:** Навигация, `Что входит` (in-scope — LX фиксировал только вне-scope),
  Нефункциональные требования, Ограничения и допущения, Глоссарий, Чек-лист ревью требований.
- **PLAN:** Цели дизайна, вся Архитектура (Контекст/Высокоуровневая/Стек), Обработка ошибок,
  Безопасность, Производительность, Тестирование, Развёртывание, Чек-лист ревью дизайна.

---

## 8. Что сохраняется как LX-специфика (нет у Kiro)

- **SPEC:** Текущее состояние (baseline), Отклонённые альтернативы, Связи (+ Second Brain `[[note]]`).
- **PLAN:** Сверка с конституцией, **Инвариант-контроль** (planned→placed маркеры).
- **`invariants.md`** целиком — durable-технический контракт-слой; у Kiro прямого аналога нет.
- **Трассировка маркеров `// SPEC NNN`** — механизм код→спека, богаче текстовой traceability Kiro.
- **Визуальные конвенции** (mermaid, EARS, правило холодного читателя, закрытый словарь emoji,
  моноширинное выравнивание широких matrix-таблиц — `|` ровными колонками в raw-diff).
